# 交叉编码器重排序评估

## 结论（TL;DR）

当前阶段**不引入**交叉编码器重排序。现有「pgvector 余弦召回 + BM25 关键词融合」已能以零额外成本命中正确文档，交叉编码器的排序精度收益不足以覆盖其延迟与 API 成本。待知识库规模与检索难度显著上升、且有量化评估证明排序精度成为瓶颈后，再重新评估。

## 现状：免费的混合排序

当前检索两阶段（见 [knowledge-qa-flow.md](knowledge-qa-flow.md)）：

1. **召回**：pgvector 余弦检索，`SearchRecallFactor=4` 放大召回（默认 limit 5 → 召回 20 个候选），过滤距离超过 `0.5` 的低相关分块。
2. **重排**：余弦距离 + 归一化 BM25 关键词分数（bigram 词元 + 候选池内局部 IDF）融合，`KeywordRelevanceWeight=0.15`。纯规则、微秒级、无额外模型调用，概念见 [bm25.md](bm25.md)。

实测：查询「蓝雀缓存雪崩如何应对？」命中正确文档，余弦距离 0.12～0.26。

## 交叉编码器的收益与成本

交叉编码器（cross-encoder / reranker，如 [bge-reranker](https://huggingface.co/BAAI/bge-reranker-base)、[Cohere Rerank](https://docs.cohere.com/docs/rerank)）是两阶段检索的第二阶段「精排」：把 query 与候选分块拼接后联合编码，直接输出相关性分数。源于 Nogueira & Cho 2019 的 [BERT re-ranking](https://arxiv.org/abs/1901.04085)。

| 维度 | bi-encoder（现有向量检索） | cross-encoder（reranker） |
| --- | --- | --- |
| 精度 | 较粗（query/document 独立编码） | 高约 15～25% |
| 延迟 | 一次向量查询（毫秒级） | 每个候选一次前向（top-20 ≈ 100～500ms，CPU） |
| 成本 | 嵌入预计算，查询免费 | 每次查询按候选数推理，无可预计算 |
| 可离线 | 是 | 否 |

关键限制：reranker 只能对第一阶段召回的候选池重排，**不能救回漏召回的正确分块**——它是精度提升，不是召回提升。

## 决策：当前不引入

1. **收益有限**：当前检索已命中正确文档（距离 0.12～0.26），reranker 的 15～25% 排序精度提升是「锦上添花」，当前数据规模下体现不出差异。
2. **成本显著**：引入 100～500ms 检索延迟 + 每次查询的 rerank API 成本，而现有 BM25 融合免费；对两段式问答（检索 + 生成）的总延迟影响明显。
3. **先优化召回而非精排**：当前知识库文档极少、检索难度低；若未来检索质量下降，更可能是召回问题（漏召回），应优先调 `SearchRecallFactor`、距离阈值或向量质量，而非加 reranker。

## 引入时机（重新评估条件）

- 知识库文档规模显著上升（数百至上千篇），检索难度提升。
- 有量化评估（命中率 / 排序质量）证明「余弦 + BM25」排序频繁出错。
- 有明确的精排收益数据支撑。

## 引入方式（若未来引入）

1. 保留现有召回 + 规则重排，在规则重排后加交叉编码器对 Top N 候选精排，返回 Top K。
2. 优先用 API reranker（项目已用 DashScope 嵌入，可复用其 rerank 模型），避免本地部署；或本地部署 bge-reranker-base（需推理服务）。
3. 交叉编码器作为 `rerank` 阶段的可选实现，保持检索行为不变。
